# Выпуск новой версии — пошаговая инструкция---

## Быстрый путь: мастер «Выпуск» в панели продаж

Открой панель продаж → вкладка **«Выпуск»** → иди по шагам, отвечая на то, что он спрашивает.
Ничего держать в голове не нужно: шаг не пропустит дальше, пока не выполнено его условие.

| Шаг | Что делает мастер |
|---|---|
| 1. Версия | Подставляет следующий номер (1.9.2 → 1.9.3), не даёт выпустить версию не старше текущей и номер не из трёх чисел |
| 2. Что нового | Берёт текст из `CHANGELOG.md`, если версия уже описана, и сохраняет правки обратно в журнал |
| 3. Обновление | Собирает подписанные установщики и заливает обновление в канал, показывая вывод сборки строка за строкой (7–12 минут) |
| 4. Проверка | Спрашивает канал от имени старой и новой версии и показывает, что ответил |
| 5. Покупателям | Публикует сборку из `D:\Релиз` новым покупателям |
| 6. Рассылка | Отправляет сообщение покупателям (текст со шага 2, можно поправить); только после подтверждения |

На шаге 4 нормальная картина такая: старая версия получает `200` с новым номером, новая — `204`.
Если наоборот, мастер подсветит строку красным, и релиз лучше не продолжать.

Мастер правит файлы репозитория и берёт сборки из `D:\Релиз`, то есть панель и репозиторий должны
лежать на этой машине — пути зашиты так же, как и остальные пути панели (`D:\TElega POST`).

## Тот же выпуск вручную

Если удобнее командная строка — те же шаги, только без ведения:

```powershell
# 1. описать изменения (текст попадёт в окно обновления)
notepad CHANGELOG.md

# 2. выпустить обновление для уже установленных копий
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/publish-update.ps1 -Version 1.9.3
```

Затем в панели продаж: вкладка **«Установщики»** → у версии 1.9.3 кнопка **«Опубликовать»**
(чтобы её получили новые покупатели) и, по желанию, вкладка **«Рассылка»** (сообщить покупателям).

Дальше — подробности обоих путей: что куда попадает, проверки и разбор частых сбоев.

---


## Куда что попадает

Новые версии расходятся **двумя независимыми путями**, и настраиваются они разными действиями:

| Кому | Что получает | Куда кладётся | Чем запускается |
|---|---|---|---|
| У кого приложение уже установлено | окно «Доступно обновление», тихая установка | Supabase Storage, публичный бакет `updates` + Edge Function `updates` | `scripts/publish-update.ps1` |
| Новые покупатели | файл установщика в чате с ботом | `sales-assets/installers/` + поле `bot_config.latest_installer_version` | панель продаж, «Опубликовать» |
| Все покупатели (сообщение) | текст в личке от бота | — | панель продаж, «Рассылка» |

Пути не связаны: можно выпустить обновление и не публиковать сборку новым покупателям (и наоборот).
`D:\Релиз` — не канал раздачи, а мастер-копия сборок: панель берёт файл оттуда.

## Разовые условия на машине

Проверить один раз, дальше они не меняются:

| Что | Зачем | Где |
|---|---|---|
| `~/.tauri/telegram-studio.key` | подпись обновлений | ключ с пустым паролем, **потеря = обновления навсегда** |
| `scripts/.secrets.env` | запись в Storage и деплой функций | `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ACCESS_TOKEN` |
| `D:\tstudio-supabase-service-key.txt` | панель пишет в Supabase напрямую | service_role ключ |
| `D:\tstudio-sales-webhook-secret.txt` | кнопки «Остановить/Запустить» бота | тот же секрет, что в Edge Function |
| Панель продаж | публикация сборок покупателям | установщик `Telegram Studio — Панель продаж_1.0.0_x64-setup.exe` |

## Шаг 1. Записать изменения в `CHANGELOG.md`

Сверху новой секцией ровно такого вида:

```markdown
## 1.9.3 — 2026-09-13

- Что изменилось для пользователя, простыми словами.
```

Этот текст скрипт вырежет и покажет в окне обновления. Если секции нет, релиз всё равно выйдет,
но окно придёт без «что нового» (скрипт предупредит об этом).

## Шаг 2. Выпустить обновление

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/publish-update.ps1 -Version 1.9.3
```

Порядок внутри скрипта:

1. подставляет `1.9.3` в `src-tauri/tauri.conf.json` — это единственный источник правды для апдейтера
   (`package.json` и `Cargo.toml` в проверке версии не участвуют);
2. собирает подписанные установщики — NSIS (`-setup.exe`, его получают покупатели и обновления) и MSI
   (только архив);
3. заливает в бакет `updates` установщик, его подпись `.sig` и манифест `latest.json`;
4. копирует NSIS-установщик в `D:\Релиз`, откуда его возьмёт панель.

Сборка release-профиля занимает **7–12 минут** и идёт с нуля (`cargo check` её не разогревает). Если
запуск прервался — просто повторите: сборка кэшируется, а `-SkipBuild` пропускает её и только
перезаливает уже готовые файлы (этим же лечится забытая секция в `CHANGELOG.md`).

Успех заканчивается строками `Copied ... to the sales-bot release folder` и
`Done. Telegram Studio 1.9.3 is offered to every installed copy on next launch.`

## Шаг 3. Проверить канал обновлений

```bash
# со стороны старой версии — должно ответить 200 и JSON новой версии
curl -s "https://xhjxnyhvfyzyulzzxpsg.supabase.co/functions/v1/updates?target=windows&arch=x86_64&version=1.9.2"

# со стороны новой — должно ответить 204 (обновления нет)
curl -s -o /dev/null -w "%{http_code}\n" "https://xhjxnyhvfyzyulzzxpsg.supabase.co/functions/v1/updates?target=windows&arch=x86_64&version=1.9.3"
```

`200` + поля `version`, `notes`, `url`, `signature` — канал живой. `204` — отвечать нечего.
`500` — манифест не залился, `401` — у функции включили проверку JWT (см. «Частые проблемы»).

## Шаг 4. Отдать сборку новым покупателям

1. Запустить панель продаж.
2. Вкладка **«Установщики»** — это содержимое `D:\Релиз`.
3. У строки `Telegram Studio_1.9.3_x64-setup.exe` нажать **«Опубликовать»**.

Панель загрузит файл в `sales-assets/installers/` и переключит `bot_config.latest_installer_version`
на `1.9.3` — именно это поле читает функция `sales-bot`, выбирая, что отправить покупателю. После
нажатия бейдж «Опубликована — отправится покупателю» переезжает на эту строку.

Проверить, что получилось:

```bash
curl -s "https://xhjxnyhvfyzyulzzxpsg.supabase.co/rest/v1/bot_config?select=latest_installer_version&id=eq.true" \
  -H "apikey: $SERVICE_KEY" -H "Authorization: Bearer $SERVICE_KEY"
# ожидаем [{"latest_installer_version":"1.9.3"}]
```

Пока этот шаг не сделан, новые покупатели продолжают получать предыдущую опубликованную версию —
даже если новая сборка уже лежит в `D:\Релиз` и уже разошлась как обновление.

## Шаг 5. Сообщить покупателям (по желанию)

Панель → вкладка **«Рассылка»** → текст → «Отправить» → подтвердить. Рассылка уходит всем уникальным
покупателям из журнала продаж (панель показывает их число) и **необратима**. Удобно вставить тот же
текст, что вы написали в `CHANGELOG.md`.

## Шаг 6. Убедиться, что всё доехало

- **Обновление:** запустить установленную копию прошлой версии — через ~2,5 секунды после старта
  должно появиться окно «Доступно обновление» с новым номером и «что нового». Кнопки: «Обновить
  сейчас» (прогресс → тихая установка → перезапуск), «Позже» (напомнит в следующий запуск),
  «Не напоминать об этой версии» (навсегда). То же окно можно вызвать без перезапуска:
  Настройки → «О программе» → «Проверить обновления».
- **Установщик для покупателей:** написать боту `/mybuild` — он присылает ту же сборку, что уйдёт
  покупателю (это админская команда без проверки покупки). В `bot_log` появится строка
  `Отправляю установщик админу (без проверки покупки): v1.9.3`.

## Если что-то сломалось

| Симптом | Причина | Что делать |
|---|---|---|
| Приложение говорит «у вас последняя версия», хотя релиз вышел | версия в запросе не старше опубликованной | проверить `curl` из шага 3 со своей версией |
| Окно обновления без «что нового» | нет секции в `CHANGELOG.md` | дописать секцию и `publish-update.ps1 -Version X -SkipBuild` |
| `curl` вернул `401` | функцию задеплоили с проверкой JWT | передеплоить с `--no-verify-jwt`; настройка закреплена в `sales-bot/supabase/config.toml` |
| `curl` вернул `500` | в бакете нет `latest.json` | запустить `publish-update.ps1 -SkipBuild` |
| Бот отвечает «Не нашёл установщик» | пустое `bot_config.latest_installer_version` | опубликовать сборку из панели (шаг 4) |
| В `bot_log`: «Установщик vX не найден в Storage» | версия опубликована, файла в бакете нет | то же: «Опубликовать» в панели |
| Панель не показывает свежую сборку | имя файла не по шаблону | в `D:\Релиз` должно быть `Telegram Studio_1.9.3_x64-setup.exe` (или `..._x64.msi`) |
| Панель пишет про отсутствующий service_role ключ | нет `D:\tstudio-supabase-service-key.txt` | положить туда ключ (только ключ, без `KEY=`) |
| Покупатель получил `.exe`, а не `.msi` | так и задумано | с 1.9.2 раздаётся NSIS: ставится без прав администратора |
| Обновление предлагается бесконечно | версия в `latest.json` выше сборки | перезалить манифест через `-SkipBuild` с правильной версией |

## Откат

**Обновление откатить вниз нельзя** — апдейтер ставит только версии выше установленной. Если релиз
сломан:

1. для новых покупателей — мгновенно вернуть предыдущую сборку: панель → «Установщики» →
   «Опубликовать» у прошлой версии (пересобирать ничего не нужно);
2. для установленных копий — починить и выпустить **новую** версию с большим номером; вернуться на
   прежний номер невозможно, апдейтер её не предложит.

## Что нельзя делать

- **Терять `~/.tauri/telegram-studio.key`.** Без него установленные копии перестанут принимать
  обновления навсегда. Сделайте копию ключа.
- **Выпускать версию не из трёх чисел.** `1.9.0.1` апдейтер отвергает; скрипт такое не пропустит.
- **Деплоить `sales-bot` без `--no-verify-jwt`.** Telegram не умеет слать заголовки Supabase, и при
  включённой проверке бот перестанет получать сообщения — продажи встанут. Настройка продублирована
  в `sales-bot/supabase/config.toml`, чтобы обычный деплой её не сломал.
- **Менять схему имён в Storage вручную.** Панель и функция должны называть файл одинаково:
  `Telegram-Studio-<версия>-x64-setup.exe` (NSIS) или `...-x64.msi` (старые сборки). Панель выводит
  имя из расширения выбранного файла, функция пробует `.exe`, затем `.msi`.
- **Править `latest.json` руками.** Его собирает `publish-update.ps1`; ручная правка — быстрый способ
  получить манифест, который клиенты отвергнут как неподписанный.
