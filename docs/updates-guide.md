# Обновления Telegram Studio — как это работает и как выпускать релиз

> Пошаговая инструкция выпуска (включая публикацию сборки покупателям и разбор частых сбоев) —
> `docs/release-runbook.md`. Ниже — как устроено внутри и почему сделано именно так.

Приложение само проверяет обновления при запуске (через 2,5 секунды после старта) и предлагает
обновиться: «Обновить сейчас», «Позже» (напомнит в следующий запуск) или «Не напоминать об этой
версии». Установка идёт без запроса прав администратора, по завершении приложение перезапускается.

Внутри приложения обновление возможно только на компьютере: Tauri-плагин апдейтера не существует
для мобильных. На Android строку проверки в настройках не показываем вовсе, чтобы не обещать
«у вас последняя версия» там, где проверить нечем.

---

## Как выпустить обновление

**Ничего никуда копировать вручную не нужно** — кроме текста «Что нового».

### 1. Записать изменения в `CHANGELOG.md`

Новая секция сверху, заголовок формата `## 1.9.3 — 2026-09-13`. Именно этот текст скрипт вырежет
и покажет пользователю в окне обновления. Если секции для версии нет, релиз всё равно выйдет, но
окно придёт без описания изменений (скрипт предупредит об этом).

### 2. Запустить публикацию

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./scripts/publish-update.ps1 -Version 1.9.3
```

Скрипт по шагам:

1. подставляет `1.9.3` в `src-tauri/tauri.conf.json` (только трёхкомпонентный semver — `1.9.0.1` нельзя,
   парсер апдейтера такое отвергнет);
2. собирает подписанные установщики: NSIS (`-setup.exe`) и MSI;
3. загружает в Supabase Storage (публичный бакет `updates`): установщик, его подпись и `latest.json` —
   **это и есть канал обновлений**;
4. копирует **NSIS-установщик** в `D:\Релиз` — это мастер-копия сборок, из неё установщик попадает
   к новым покупателям (шаг 3 ниже). MSI остаётся в папке сборки как архив и покупателям больше не
   выдаётся.

Прерванный запуск можно продолжить: сборка кэшируется, а `-SkipBuild` пропускает сборку и только
перезаливает уже готовые артефакты.

### 3. Опубликовать сборку новым покупателям

Автоматическое обновление (шаг 2) видят только те, у кого приложение уже установлено. Чтобы
установщик получали **новые** покупатели, его нужно отдельно опубликовать:

1. запустить `sales-bot/control-panel/run-dev.ps1`;
2. вкладка **«Установщики»** → у нужной версии нажать **«Опубликовать»**.

Панель загружает файл в `sales-assets/installers/` и переключает `bot_config.latest_installer_version` —
именно это поле читает функция `sales-bot` для решения, какой файл отправить. Без этого шага бот
продолжает отдавать предыдущую опубликованную версию, даже если сборка уже лежит в `D:\Релиз`.

Публикация версии — независимое действие от выпуска релиза: можно выпустить обновление и не
публиковать сборку, и наоборот.

### 4. Проверить канал

```bash
curl -s "https://xhjxnyhvfyzyulzzxpsg.supabase.co/functions/v1/updates?target=windows&arch=x86_64&version=1.9.2"
```

- `200` + JSON с новой версией — обновление предложено всем, у кого версия ниже;
- `204` — обновления нет (версия в запросе не старше опубликованной).

## Что где лежит

| Что | Где | Кто использует |
|---|---|---|
| Установщик обновления, подпись, манифест | Supabase Storage, бакет `updates` | встроенный апдейтер приложения |
| Эндпоинт проверки | Edge Function `updates` (Supabase) | встроенный апдейтер приложения |
| Установщик NSIS | `D:\Релиз` | мастер-копия; отсюда его публикует панель продаж |
| Опубликованный установщик | Supabase Storage, `sales-assets/installers/` | функция `sales-bot` (раздача покупателям) |
| Установщики прошлых версий | `D:\cargo-tgt\release\bundle\{nsis,msi}\` | архив, вручную |

Обе Edge-функции задеплоены **с выключенной проверкой JWT** (`--no-verify-jwt`, зафиксировано в
`sales-bot/supabase/config.toml`): апдейтер делает обычный GET без заголовков Supabase, а Telegram
вообще не умеет их слать, поэтому при включённой проверке `updates` отдавала бы `401` на каждой
проверке обновления, а `sales-bot` — на каждом сообщении покупателя, то есть продажи встали бы.
Настройка для `sales-bot` теперь тоже лежит в `config.toml`, чтобы обычный
`supabase functions deploy sales-bot` не выключил её молча. Настройка канала — `scripts/setup-update-channel.ps1`
(создаёт бакет, деплоит функцию, прогоняет проверку; можно запускать повторно).

Ключи скриптов лежат в `scripts/.secrets.env` (в git не попадает): `SUPABASE_SERVICE_ROLE_KEY` —
нужен для записи в Storage, `SUPABASE_ACCESS_TOKEN` — только для деплоя функции.

## Что важно не потерять

**Ключ подписи `~/.tauri/telegram-studio.key`.** Если его потерять, уже установленные копии
перестанут принимать обновления — навсегда, восстановить это можно только выпуском новой версии,
которую невозможно доставить. Сделайте копию. Пароля у ключа нет (хранится с пустым), поэтому
скрипты выставляют `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` пустым явно: если переменную просто удалить,
tauri начнёт спрашивать пароль в консоли и в неинтерактивном запуске это выглядит как зависание.

**Формат установщика — один на всё.** И обновления, и новые установки идут NSIS-установщиком
(`bundle.windows.nsis.installMode = currentUser`), поэтому без запроса прав администратора. Держать
для покупателей MSI нельзя: он ставится per-machine в `Program Files`, NSIS — per-user в профиль, и
после первого обновления на машине окажутся две копии приложения. Переход MSI → NSIS поддерживается,
обратный — нет, поэтому формат меняют именно у новых установок.

Формат виден в имени объекта: NSIS публикуется как `Telegram-Studio-<версия>-x64-setup.exe`, старые
сборки лежат как `Telegram-Studio-<версия>-x64.msi`. Панель берёт расширение из выбранного файла,
а функция `sales-bot` пробует сначала `.exe`, потом `.msi` — поэтому уже опубликованные версии
продолжают работать. Панель показывает в списке оба формата и при равной версии ставит NSIS выше
(на первую строку), чтобы «последняя сборка» указывала именно на него.

**Версия — только `X.Y.Z`.** `1.9.0.1` из старого журнала апдейтер и MSI не примут.

## Как проверить обновление вживую

Проверка обновлений появилась только в `1.9.2`. Значит, уже установленная `1.9.1` окна не покажет
никогда — первый клиент, способный его увидеть, это `1.9.2`, и увидит он обновление, когда выйдет
`1.9.3`. Варианты проверки:

1. **Честный**: выпустить `1.9.3` (пусть даже пустую) и ждать окна на `1.9.2`.
2. **Быстрый**: временно поднять версию в манифесте, не выпуская релиз — установленная `1.9.2`
   увидит «1.9.3», скачает и поставит тот же установщик. После проверки версию в `latest.json`
   **обязательно вернуть обратно**, иначе обновление будет предлагаться бесконечно.
