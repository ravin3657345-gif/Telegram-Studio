# Обход блокировки Telegram Bot API — технический документ

**Дата:** 2026-07-23
**Статус:** реализовано и проверено вживую

---

## 1. Проблема

Часть пользователей (в первую очередь из России) не может достучаться до
`api.telegram.org` напрямую — провайдер блокирует соединение. Приложение
должно уметь публиковать посты даже в этом случае, без участия пользователя.

## 2. Как именно выглядит блокировка (проверено вживую 2026-07-22/23)

Раньше в проекте считалось, что блокировка происходит на уровне TCP —
SYN-пакет просто не доходит, до TLS дело не доходит вообще. Живая проверка
это опровергла:

- **TCP-соединение проходит нормально** (SYN/ACK за ~10 мс)
- Обрыв происходит **на TLS-рукопожатии** — соединение сбрасывается сразу
  после отправки ClientHello
- Проверка с **поддельным SNI** (тот же IP `api.telegram.org`, но домен в
  TLS ClientHello — `example.com`) сбрасывается точно так же. Значит,
  блокировка идёт **не по содержимому SNI**, а по самому IP-адресу
  Telegram — просто триггерится не на SYN, а чуть позже, на TLS-слое
- Это делает бессмысленными любые трюки с фрагментацией TLS-рукопожатия
  (пробовали раньше, см. `fragmented.rs`, ныне удалён) — фрагментация не
  прячет IP назначения, только содержимое пакета

Отдельная, независимая находка — **лимит на размер одного запроса**:
- Прямые запросы к **любому** Edge Function на Supabase (`functions/v1/*`),
  а также напрямую к **Storage** (`storage/v1/*`) при загрузке одним
  запросом, обрываются, если тело запроса больше **~25–30 КБ**. Порог не
  зависит от `Content-Type` (проверено и на `multipart/form-data`, и на
  `application/octet-stream`)
- Порог **нестабилен во времени** — предположительно ISP донастраивает
  правила DPI. Один раз живьём прошла загрузка 6 МБ одним запросом в
  Storage, а буквально на следующий день тот же путь резался уже на ~28 КБ
- **Много параллельных мелких запросов** (~20 КБ каждый) к Storage
  проходят нормально, даже когда единый большой запрос — нет. Но при
  **устойчивой долгой передаче** (сотни КБ, много секунд) даже маленькие
  запросы иногда начинают падать — какой-то дополнительный лимит по
  суммарному объёму/времени, не только по размеру одного запроса

## 3. Архитектура обхода

### 3.1 Общая схема

```
Публикация поста
       │
       ▼
┌──────────────────┐
│ Прямое подключение │ ──── успех ──────────────────────► готово
│ к api.telegram.org │
└──────────────────┘
       │ сетевая ошибка
       ▼
┌───────────────────────────────────┐
│ Резервный путь через Supabase relay │
│ (Edge Function tg-relay)           │
└───────────────────────────────────┘
       │
       ├── обычный текст (JSON) ──► напрямую транзитом в Telegram
       │
       └── файл (фото/видео/документ) ──► см. 3.3, путь через чанки
```

Прямое подключение пробуется **всегда первым**. Резервный путь включается
только при сетевой ошибке (не при логической ошибке Telegram — например
неверный `chat_id` — ретраить другим транспортом её бессмысленно).

### 3.2 Текстовые посты — простой транзит

Файл: `sales-bot/supabase/functions/tg-relay/index.ts`, маршрут
`/tg-relay/bot<token>/<method>`.

Edge Function просто пересылает тело запроса и `Content-Type` как есть на
`api.telegram.org/bot<token>/<method>` и возвращает ответ Telegram
дословно. Маленький JSON-запрос почти всегда укладывается в лимит ~25–30 КБ,
поэтому для текста этого достаточно.

Авторизация — штатная JWT-проверка Supabase (`verify_jwt: true`) по
встроенному в приложение publishable-ключу, тот же механизм, что уже
использовался для активации лицензий.

### 3.3 Файлы (фото/видео/документы/вложения Rich-постов) — путь через чанки

Поскольку прямой запрос с файлом почти всегда больше разрешённого порога,
единственный рабочий вариант — не посылать файл единым запросом вообще.

**Клиент** (`src-tauri/src/telegram/client.rs`, функция
`call_multipart_via_storage`):

1. Файл режется на кусочки по **20 КБ** (`CHUNK_SIZE`) — с запасом от
   измеренного порога ~25–28 КБ
2. Кусочки грузятся в приватный Storage-бакет `relay-tmp` под случайным
   путём `relay-tmp/<uuid>/<00000>`, `<00001>`, ... — с ограничением
   **8 параллельных загрузок одновременно** (`CHUNK_CONCURRENCY`,
   через `tokio::sync::Semaphore`)
3. Когда все кусочки загружены, клиент шлёт в Edge Function **маленький**
   JSON: `{ fields: {...текстовые поля...}, files: [{ field, chunkPaths,
   fileName, mimeType }] }` — на маршрут
   `/tg-relay/storage/bot<token>/<method>`

**Edge Function** (`handleStorageForward` в том же `index.ts`):

1. Скачивает все чанки данного файла параллельно через `service_role`
   (это уже с серверов Supabase, не через интернет пользователя — тут лимит
   ISP не действует)
2. Склеивает их обратно в правильном порядке (порядок кодируется прямо в
   имени чанка — `00000`, `00001`, ...)
3. Собирает `multipart/form-data` и шлёт в `api.telegram.org` как обычно
4. Возвращает ответ Telegram клиенту
5. **В `finally`** — удаляет все чанки данного файла из Storage, вне
   зависимости от успеха или ошибки

**Самоочистка бакета.** Помимо удаления «своих» чанков сразу после
использования, при каждом вызове Edge Function попутно (не блокируя ответ)
проверяет весь бакет `relay-tmp` и удаляет любые чанки старше 10 минут —
подстраховка на случай, если клиент загрузил чанки, но так и не дошёл до
шага 3 (упал, потерял связь и т.д.). В норме в бакете не задерживается
ничего дольше нескольких секунд одного запроса.

**Права доступа.** Бакет `relay-tmp` — приватный (`public: false`).
Клиентский (встроенный в приложение, по сути публичный) ключ имеет только
право `INSERT` — может грузить, не может ни прочитать, ни удалить чужую
загрузку. Чтение и удаление — только через `service_role` внутри Edge
Function.

### 3.4 Результаты живого тестирования (2026-07-23)

| Размер | Способ | Результат |
|---|---|---|
| 1 файл, 500 КБ, один запрос | напрямую в Storage/Functions | 100% обрывается |
| 50 чанков × 20 КБ (~1 МБ, размер фото) | параллельно, `Promise.all` | 50/50 успех, **1.85 сек** — почти как обычная загрузка |
| 250 чанков × 20 КБ (~5 МБ, размер видео), без ограничения параллелизма | все разом | 158/250 успех, много таймаутов |
| 250 чанков × 20 КБ (~5 МБ), ограничение 15 параллельно | пул воркеров | 147/250 успех, **108 сек** — заметно хуже |

**Вывод**: схема надёжно чинит публикацию фото (типичный размер
укладывается в секунды, почти без потери скорости). Для видео и крупных
документов — работает лучше, чем ничего, но не гарантированно; для них
известное, принятое ограничение, отдельно не решалось.

## 4. Что было опробовано и отброшено

- **Фрагментация TLS ClientHello** (`fragmented.rs`, ныне удалён) — была
  основана на предположении, что блокировка идёт на уровне SYN, до TLS.
  Живая проверка это опровергла (см. раздел 2) — фрагментация не может
  спрятать IP назначения, только содержимое, а блокировка триггерится
  именно по IP
- **WinDivert (packet-level bypass)** — собственная реализация на основе
  техники GoodbyeDPI, пробовали фрагментировать TCP-сегменты на уровне
  пакетов. Живое тестирование показало, что удалённая сторона (похоже,
  Cloudflare перед Supabase) детектирует и сбрасывает соединение
  независимо от точки разбиения и задержки между фрагментами. Функция
  отключена в настройках, код оставлен в дереве как справочный
  (`src-tauri/src/telegram/winbypass.rs`)

## 5. Ключевые файлы

| Файл | Роль |
|---|---|
| `src-tauri/src/telegram/client.rs` | Клиент: прямое подключение → relay, включая чанкование файлов |
| `src-tauri/src/telegram/form.rs` | Обёртка над multipart-формой, даёт доступ к полям для сборки JSON-дескриптора |
| `sales-bot/supabase/functions/tg-relay/index.ts` | Edge Function: простой транзит для текста + сборка чанков для файлов |
| Supabase Storage, бакет `relay-tmp` | Приватное временное хранилище чанков |

## 6. Известные ограничения

- Видео и крупные документы (от нескольких МБ) — резервный путь работает
  ненадёжно, полноценно не решено
- Порог блокировки (~25–30 КБ) измерен на конкретный момент времени и
  может измениться — константа `CHUNK_SIZE` (20 КБ) заложена с запасом,
  но не отслеживается автоматически
